# Reproducibility materials: synchronization assurance for IoT-enabled digital twins

Code and generated data accompanying the submitted manuscript by **Ilyes Ahmim and
Abderrezak Rachedi**:

> Synchronization Assurance for IoT-Enabled Digital Twins: A Review of Cross-Layer
> Threats, Protocols, Standards, and Indicators

This repository reproduces the closed-form analysis in Section 7.2, the simulation
in Section 8.6 and the simulation appendix, and the message-size computations in Sections 5.2
and 8.6. Figure and table numbers below refer to the submitted manuscript.

The data are generated by analytical models and simulations. No external dataset,
credentials, network service, physical sensor, broker, or hardware testbed is needed
to run the analyses. Internet access is only needed to install the Python dependencies.

## Reproduce all results

Tested on Linux with **Python 3.12**. From this repository's root:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-lock.txt
python run_all.py
```

On Windows, create the environment with `py -3.12 -m venv .venv` and activate it
with `.venv\Scripts\Activate.ps1` in PowerShell. The remaining commands are the same.

`requirements-lock.txt` records the complete dependency versions used for the
verification; `requirements.txt` lists the five direct dependencies. The scripts
use a noninteractive plotting backend, so no graphical desktop is required.

The runner executes all three scripts and then checks the generated results against
the reference data. Allow a few minutes, depending on the computer. Outputs go to
`results/reproduced/`, leaving the reference files intact. A successful run ends
with `PASS` messages. It also saves:

- `environment.json`: Python, platform and direct dependency versions;
- `logs/`: full output of each script, including the Monte Carlo and false-alarm checks;
- `verification.json`: results of the comparison with the reference data.

To check an existing run again, use `python verify_results.py`. A different output
directory can be selected with `python run_all.py --output /path/to/output`.

The three scientific scripts preserve the original default computations. The audit

the simulation results are in Table XIII, and parameters are defined in the `Params`

`verify_results.py` compares results and does not alter the scientific model.

Individual scripts write into the current working directory. To run one alone
without changing the reference data, for example:

```bash
mkdir -p results/reproduced
cd results/reproduced
python ../../scripts/coap_timeliness.py
python ../../scripts/dt_sync_sim.py
python ../../scripts/cose_overhead.py
```

The first two scripts also accept an existing output directory as a positional
argument. `sim_table.tex` is a generated table-body fragment for inclusion in the
manuscript, not a standalone LaTeX document. No TeX installation is needed to run
the analyses or generate the figures.

## Expected findings

- At transmission loss probability `p = 0.2`, CoAP delivery probability is `0.99968`;
  timely delivery probabilities are `0.80`, `0.96`, and `0.992` for freshness bounds
  of 2, 5, and 10 seconds. The Monte Carlo check uses 400,000 trials per point.
- The simulation runs four scenarios (`none`, `replay`, `delay`, `spoof`) and four
  configurations (`C0` to `C3`) with 30 seeds each: **480 runs**. Separate 10-hour
  runs check false alarms for C2 and C3, without attacks or degradation.
- Under replay, C0 reports mean state age near `0.28 s` while true observation age
  averages about `180.3 s`. Under spoofing, C3 detects the inconsistency about
  `4.48 s` after degradation begins, averaged across the 30 seeds.
- Plain CBOR occupies **23 bytes**. COSE_Sign1 with Ed25519 or ES256 occupies
  **100 bytes** (77 bytes extra). COSE_Mac0 with HMAC-256/64 occupies **43 bytes**
  (20 bytes extra).

## Data, seeds and reproducibility

`results/reference/` contains the original supplementary outputs, including all
480 per-run indicator rows, 51 CoAP probability rows, aggregate results, the table
fragment and both figures in PDF and PNG. These files are included in the repository.
`results/reproduced/` is ignored by Git because it can be regenerated.

The simulation seed is `1000 * scenario_index + seed_index`, where scenarios are
ordered `none, replay, delay, spoof` and `seed_index` ranges from 1 to 30. Figure 8
uses seed 7; each false-alarm run uses seed 99. The CoAP Monte Carlo uses seed 1 for
each tested parameter pair. See [the data dictionary](docs/DATA_DICTIONARY.md)
for column definitions, units, averaging windows and missing values.

Numerical CSV and summary values are compared with absolute and relative tolerances
of `1e-9`; table-body text and byte counts are compared exactly. Host cryptographic
timings vary and are excluded. The COSE script generates fresh temporary signing
keys on each run, but the encoded sizes are fixed. No signing keys are saved.
PDF metadata, fonts and rendering can vary across systems, so PDF/PNG files are
not required to be byte-identical. See [the validation record](docs/VALIDATION.md).

The original JSON summaries retain Python's `NaN` notation for undefined indicators;
strict JSON consumers must convert these values to `null`. CSV represents them as
`nan`; the generated table uses dashes. These values are not zeros.

## Scope and limitations

The simulation is an illustrative event model, not a deployed security system.
Signature validity is represented by a Boolean and replay rejection by a monotone
sequence check on a FIFO path. It does not perform cryptography, simulate full
protocol stacks or broker internals, or measure processor, energy or hardware costs.
The separate COSE script performs actual example encodings and cryptographic
operations, with a fixed illustrative MAC key and one-byte key identifier; it is
not production key-management code.

Protective-action times are recorded, but the modeled vibration trajectory continues
after a hold; state-error metrics therefore describe the observation model, not
the physical response of a stopped machine. The attacks are stylized and nonadaptive.
An attacker able to manipulate both vibration and independent current consistently
could evade C3. The figures and indicators are not measurements of a deployment.

## Scientific audit supplement (5 November 2026)

After the full reproduction, run:

```bash
python scripts/audit_analysis.py
```

This writes CSVs in the parent manuscript's `results/` directory. It computes
Student-t mean intervals, within-seed paired contrasts, Wilson intervals for
run-level detection, and 1,470 targeted sensitivity/control runs. It also verifies
CoAP probabilities by enumerating loss sequences and integrating over the timeout,
checks illustrative correlated-loss sensitivity, and serializes fixed-length
post-quantum signature placeholders to verify overhead (not signing performance).
See `../reports/simulation_validation.md` and `../reports/math_audit.md` for the
methods, actual results and limitations. The main script now prints the exact
observed CoAP discrepancy to six decimals: .002110, within the revised .0022 bound.

The optional simulator argument `freshness_margin=PARAMS.CLOCK_ERR` applies the
conservative 5 ms clock guard. `rewrite_replay_timestamp=False` preserves the source
signature during replay and isolates old-sequence rejection. Both defaults preserve
the archived computation. The original table fragment remains an archival output;
the corrected manuscript distinguishes the no-attack C0 mean age from C1–C3.

`requirements-audit-lock.txt` records the packages actually used in the November
audit; the original `requirements-lock.txt` is retained. `SHA256SUMS.txt` records
the original scientific scripts and reference files; after the documented code
changes, use `SHA256SUMS-audit.txt` for current scripts and original reference files.
The original reference-file hashes are unchanged.

On 6 November, an independent review corrected a startup edge case in C3: a
current sample marked lost is now excluded even when it is the first sample.
All 120 C3 baseline and 810 C3 sensitivity runs retained the same recorded
results within `1e-12`, and the full original workflow passed again. To repeat
that targeted comparison against saved outputs, run
`python scripts/check_current_sample_loss.py`. The correction and its executed
checks are documented in `../reports/simulation_validation.md`.
